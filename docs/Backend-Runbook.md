# Передай · запуск backend v0.1

Реализация HTTP API находится в `server/`, машинный контракт — в [`server/openapi.json`](../server/openapi.json), схема — в [`server/migrations/001_init.sql`](../server/migrations/001_init.sql). Для работы нужен PostgreSQL и Node.js версии из README. Владелец схемы и прикладная роль используют разные учётные данные. Скрипт демо заполняет только локальную частичную кампанию, не производственную.

## Подготовка БД

1. Создайте отдельную пустую БД `peredai`; для миграции назначьте учётную запись, имеющую права создавать таблицы, функции, триггеры и глобальную роль `peredai_runtime` (`CREATEROLE` либо административный запуск). Не выполняйте миграции от имени HTTP-приложения.
2. Из корня репозитория запустите `DATABASE_URL='postgresql://schema_owner:...@127.0.0.1:5432/peredai' npm run server:migrate`. Это миграция для пустой БД; повторный запуск намеренно завершится ошибкой и не является механизмом обновления схемы.
3. Администратор создаёт отдельный LOGIN для HTTP-приложения и выдаёт ему **только** членство в роли, созданной миграцией:

   ```sql
   CREATE ROLE peredai_app LOGIN INHERIT PASSWORD '<уникальный пароль>';
   GRANT peredai_runtime TO peredai_app;
   GRANT CONNECT ON DATABASE peredai TO peredai_app;
   REVOKE CREATE ON SCHEMA public FROM PUBLIC;
   ```

   Пароль передаётся секретом окружения, не сохраняется в репозитории. Приложение не должно подключаться как владелец схемы, суперпользователь или роль с `CREATEROLE`. Для текущей схемы приложение читает каталог и кампанию, вставляет сессии и результаты, берёт блокировку строки кампании; триггер не разрешает роли менять настройки кампании.

## Локальная проверка частичного демо

1. Заполните `PEREDAI_BRAND` и `PEREDAI_OFFER` согласованным демо-текстом, `PEREDAI_MAX_CREATURES` явным положительным числом. С владельцем схемы запустите `npm run server:seed-demo`. По умолчанию кампания доступна для чтения, запись закрыта. Для проверки сквозного сценария **только на loopback** установите `PEREDAI_ALLOW_PARTIAL_DEMO=1` до запуска seed. Этот флаг нельзя применить к уже созданной кампании повторным запуском seed.
2. Установите `DATABASE_URL` с логином `peredai_app`, `PEREDAI_PUBLIC_ORIGIN=http://127.0.0.1:5173`, два разных случайных секрета от 32 символов в `PEREDAI_CURSOR_SECRET` и `PEREDAI_CSRF_SECRET`. В одном терминале запустите `npm run server:dev`; во втором — `VITE_API_MODE=live npm run dev`. Vite передаёт `/api/v1` на `127.0.0.1:8787`.
3. Проверьте `GET /api/v1/health` через Vite, затем браузерный сценарий с двумя независимыми профилями. Исходные изображения есть только для шагов 1–4. Шаги 5–16 недоступны для сохранения, пока не подготовлены и не утверждены 36 PNG и полный каталог.

## Одна production-аппа

1. В среде сборки задайте `VITE_CAMPAIGN_SLUG` и выполните `npm ci`, `npm run build:production`. Эта команда принудительно собирает `VITE_API_MODE=live`, создаёт `dist/`, `server-dist/` и метаданные со slug. Принесите обе директории и production-зависимости `node_modules` в runtime-пакет; исходный Vite-сервер там не нужен. `npm run build` без live-флага пригоден для обычной проверки, но `start:production` его отвергнет.
2. На пустой БД мигрируйте **владельцем схемы**: `DATABASE_URL=... node server-dist/migrate.js`. Настройте `peredai_app` по инструкции выше. Миграция не запускается автоматически при старте и не повторяется при каждом обновлении.
3. Создайте кампанию административной ролью. Для закрытого HTTPS staging с 12 имеющимися PNG предусмотрено `PEREDAI_STAGING=1 npm run server:seed-staging` с явными `DATABASE_URL`, `PEREDAI_PUBLIC_ORIGIN`, `PEREDAI_CAMPAIGN_SLUG`, `PEREDAI_BRAND`, `PEREDAI_OFFER`, `PEREDAI_MAX_CREATURES`. Используйте **отдельную БД с `staging` в имени** и ограничьте доступ к staging на ingress. Скрипт не удаляет данные, не задаёт реальный бренд/CTA и не меняет локальный `server:seed-demo`. После проверки изолированная staging-БД удаляется администратором отдельным разрешённым действием. Для публичной кампании нужны согласованные D01–D04 и полный каталог.
4. В runtime задайте `DATABASE_URL` с ролью `peredai_app`, **явный** `PEREDAI_PUBLIC_ORIGIN`, совпадающий `PEREDAI_CAMPAIGN_SLUG`, два различных секрета, положительные лимиты и `PEREDAI_SHUTDOWN_GRACE_SECONDS`. `PORT` берётся у хостинга, иначе действует `PEREDAI_PORT` или 8787; если `PORT` и `PEREDAI_PORT` указаны вместе, они должны совпадать. HTTPS по умолчанию слушает `0.0.0.0`, локальный HTTP — только `127.0.0.1`; `PEREDAI_BIND_HOST` может явно выбрать IP с тем же ограничением для HTTP. Локальный HTTP origin обязан иметь тот же порт, что слушатель. Запуск: `npm run start:production`. Отсутствие `dist/index.html`, live-сборки или кампании приводит к отказу до открытия порта.
5. Один HTTPS ingress передаёт **весь** трафик на один порт Node.js; Node сам отдаёт SPA и API. `GET /api/v1/health` проверяет БД. На HTTPS обязателен один из режимов `PEREDAI_RATE_LIMIT_MODE`: `trusted-proxy` требует `PEREDAI_TRUSTED_PROXY_ADDRESSES` и единственный IP в очищенном прокси заголовке `X-Forwarded-For`; запросы с недоверенного адреса сокета отклоняются `403 PROXY_REJECTED`, прямой внешний доступ к Node также закрывается на инфраструктуре. `ingress` отключает внутренний bucket и требует ограничения POST на границе сети. В режиме `ingress` отсутствие внешнего лимита оставит создание профилей без защиты; один лишь флаг не заменяет ingress. Случайный заголовок от посетителя не должен попасть в Node как доверенный. При нескольких репликах лимит должен быть общим.

Проверка после обновления: `/`, `/mine`, `/s/{token}`, реальный PNG, неизвестный ассет и неизвестный API-путь; затем bootstrap, два браузерных профиля, вклад и точный повтор команды. Сравните slug из `server-dist/build-meta.json` со значением в окружении и записью БД. При неудаче верните предыдущие `dist/` и `server-dist/` **как один совместимый комплект**; если выпуск менял схему, сначала проверьте совместимость схемы с предыдущим комплектом. В текущей доработке новой миграции нет.

## Эксплуатация и проверки

- `npm test` проверяет контракт на PGlite и локальный HTTP, а также frontend; `npm run build` проверяет типы и собирает оба приложения. PGlite исполняет PostgreSQL-совместимую схему, но не доказывает порядок транзакций на двух соединениях настоящего PostgreSQL. Перед внешним запуском требуются реальные конкурентные испытания и браузерная приёмка.
- `/api/v1/health` делает `SELECT 1` и отвечает `200 {"status":"ok"}` при доступной БД. Заголовок `X-Request-Id` даёт идентификатор запроса; неожиданная ошибка логирует только его, код и класс ошибки. Секреты cookie, тела и SQL не логируются. Следите за долей 5xx, 429, временем ответа, доступностью БД, заполнением кампании и ростом таблиц.
- Для резервной копии нужны согласованные снимки БД **вместе с версиями ассетов** и отдельное сохранение ролей/конфигурации. Проверяйте восстановление на изолированной БД. Периодичность, хранение, допустимая потеря данных и порядок удаления ещё не согласованы; автоматическая очистка не выполняется.
- Ошибку после отправки команды клиент разрешает повтором того же ключа, тела, цели и профиля. Запись результата и receipt атомарны. При утере cookie нельзя переносить pending-команду на другой профиль.

## Открытые решения для внешнего запуска

D01 — повторное участие предка в цепочке; сейчас ответ `ANCESTOR_POLICY_UNRESOLVED`. D02 — окончательное правило анонимного профиля и потери доступа. D03 — бренд, оффер, CTA и полный каталог иллюстраций. D04 — сроки сессий и хранения, значения rate limits/квоты, backup/RPO/RTO. Пока решения не приняты, локальный частичный демо-режим не следует объявлять публичным запуском.
