# Передай — ТЗ базы данных v0.1

Дата: 22 сентября 2026. Статус: **проект технического решения для согласования**.
Результат этого задания — спецификация. Миграции, БД, резервирование и испытания не выполнены.
Связанный контракт API: [Peredai-Backend-TZ-v0.1.md](Backend-TZ.md); интерфейс: [Peredai-Frontend-TZ-v0.1.md](Frontend-TZ.md).
Основание: подтверждённая механика 16 последовательных вкладов и общий контракт трёх ТЗ от 22.09.2026. Он заменяет прежнюю возможность произвольного редактирования опубликованного существа.

## 1. Назначение и границы

БД хранит неизменяемые вклады, их происхождение, снимки внешности, публичные ссылки, анонимные профили и результаты команд одного backend.
СУБД — PostgreSQL; конкретная версия, хостинг и ресурсы не выбраны. Одна транзакция не выходит за пределы этой БД.
Согласовано: один участник добавляет один шаг; корень выбирает B01/B02/B03, шаги 2–16 — одну опцию соответствующего номера A/B/C; ветви независимы; после шага 16 добавления нет.
**Проектные предложения P2/P3:** один результат на ссылку и серверный профиль; возврат в анонимном профиле браузера. Профиль не доказывает уникальность человека.
**D-01 открыт:** допустим ли новый вклад профиля, уже встречавшегося среди более ранних предков. Запрет прямого продолжения собственного узла определён; правило для более дальнего предка не выбрано.
Платежи, CRM, отправка сообщений, административный веб-интерфейс и бинарные изображения внутри БД не входят в объём.

## 2. Представление состояния

Предлагается единственный источник внешности: JSONB `CreatureRevision.appearance` в формате `Appearance`.
Формат: `{base_id,choices:[{step,choice_id},...]}`; корень имеет пустой `choices`; элементы потомка упорядочены по шагам 2..n.
Каждый `Creature` имеет ровно одну неизменяемую `CreatureRevision`. Нет `current_revision_id`, истории последующего редактирования или команды исправления уже принятого выбора.
Отдельную таблицу выборов и независимо изменяемые `base_id`, `step`, `is_complete` не создавать: иначе появятся конкурирующие источники состояния.
`step = 1 + length(appearance.choices)`; `total_steps = 16`; `is_complete = (step = 16)` вычисляются при чтении проверенного снимка.
Цена JSONB — проверка формы и межстрочного наследования, а также повторение короткого префикса в каждом узле. Длина ограничена 15 дополнениями; аналитические запросы по каждому выбору сейчас не нужны.
Нормализованную таблицу выборов можно пересмотреть при новых подтверждённых запросах; миграция должна сохранить один источник истины и DTO.

## 3. Таблицы, поля и типы

Имена ниже — логические имена модели; физическое именование допускает единое snake_case без изменения API. Все перечисленные поля NOT NULL, кроме явно отмеченных NULL.
Для идентификаторов предлагается `uuid`; способ генерации фиксируется при реализации. Все даты — `timestamptz`. Публичный ID не является полномочием доступа.

| Таблица | Поля и типы | Ключи / назначение |
|---|---|---|
| `CatalogVersion` | `version text`, `manifest jsonb`, `created_at timestamptz` | PK `version`; неизменяемый каталог и размещение ресурсов |
| `Campaign` | `id uuid`, `slug text`, `brand text`, `offer text`, `cta_target text`, `active_catalog_version text`, `accepts_contributions boolean`, `max_creatures bigint`, `created_at timestamptz` | PK `id`; UNIQUE `slug`; FK версии каталога; `max_creatures > 0` |
| `AnonymousProfile` | `id uuid`, `session_secret_hash bytea`, `created_at timestamptz`, `expires_at timestamptz` | PK `id`; UNIQUE представления секрета; срок задаётся согласованной политикой |
| `Creature` | `id uuid`, `campaign_id uuid`, `owner_profile_id uuid`, `origin_share_id uuid NULL`, `revision_id uuid`, `created_at timestamptz` | PK `id`; FK кампании, профиля, исходной ссылки; NULL origin только у корня |
| `CreatureRevision` | `id uuid`, `creature_id uuid`, `catalog_version text`, `appearance jsonb`, `created_at timestamptz` | PK `id`; UNIQUE `creature_id`; FK существа и каталога; один снимок на вклад |
| `ShareLink` | `id uuid`, `public_token text`, `source_revision_id uuid`, `created_at timestamptz` | PK `id`; UNIQUE `public_token`; UNIQUE `source_revision_id`; FK ревизии |
| `OperationReceipt` | `profile_id uuid`, `operation_type text`, `idempotency_key text`, `normalized_target jsonb`, `normalized_body jsonb`, `state text`, `http_status smallint NULL`, `response_body jsonb NULL`, `created_at timestamptz`, `completed_at timestamptz NULL` | Составной PK `(profile_id,operation_type,idempotency_key)`; FK профиля; окончательный ответ команды |
| `ClientEvent` | `profile_id uuid`, `event_id uuid`, `creature_id uuid`, `kind text`, `received_at timestamptz` | Составной PK `(profile_id,event_id)` обеспечивает UNIQUE этой пары; FK профиля и существа; `kind = 'cta_click_reported'` |

Форма manifest и система координат определены в §8.1 ТЗ frontend; БД сохраняет этот JSON без переименования полей. До активации manifest проверяется на 3 базы B01/B02/B03 и ровно 3 варианта 02A..16C для каждого следующего шага; набор доступен независимо от прежних выборов. Ссылки на ресурсы и размещение на каждой базе фиксируются в версии, без выдуманных координат.
`operation_type` имеет три значения: `create_root`, `create_offspring`, `create_share`; отображение методов API в эти значения одинаково в backend и БД.
`normalized_target` включает каноническую цель команды; `normalized_body` — все значимые поля её запроса. Сравнение выполняется по нормализованным значениям, не только по хешу.
`response_body` содержит исходный `ContributionResult` либо `ShareView`; `http_status` — исходный успешный 200/201. Повтор воспроизводит сохранённый статус и тело.
`state` имеет только `pending` и `completed`. Pending существует исключительно внутри незавершённой транзакции; его публикация через COMMIT запрещается отложенной проверкой.
У pending статус, тело и completed_at равны NULL; у completed они обязательны. После завершения receipt не изменяется.
Кампания события определяется через `ClientEvent.creature_id → Creature.campaign_id`; второй изменяемый campaign_id в событии не нужен.
Секрет cookie в открытом виде, CSRF-токен и URL чужих ссылок в аналитике не сохраняются. Алгоритм представления session-секрета согласуется с backend.

## 4. Кратности и целостность связей

- `Campaign 1:N Creature`; `AnonymousProfile 1:N Creature`; ни одна из этих связей не ограничивает профиль одним вкладом на кампанию.
- `Creature 1:1 CreatureRevision` на каждой зафиксированной версии БД; временный промежуток между INSERT внутри транзакции наружу не виден.
- `CreatureRevision 1:0..1 ShareLink`; одна публичная ссылка переиспользуется для одной неизменяемой ревизии, включая финал шага 16.
- `ShareLink 1:N Creature` через `origin_share_id`; каждый потомок имеет ровно одну исходную ссылку.
- `Creature 1:N ClientEvent`; `AnonymousProfile 1:N ClientEvent` и `1:N OperationReceipt`.
- Единственный путь к родителю: `Creature.origin_share_id → ShareLink.source_revision_id → CreatureRevision.creature_id`.
- Отдельные parent_id/root_id в таблице Creature не добавлять. `parent_id` и `root_id` в запросе family обозначают область чтения, а не новые источники происхождения.
- Предлагаемый механизм точной пары: UNIQUE `(creature_id,id)` у ревизии; FK `(Creature.id,Creature.revision_id) → CreatureRevision(creature_id,id)` и обратный FK ревизии на Creature — DEFERRABLE INITIALLY DEFERRED.
- UNIQUE `CreatureRevision.creature_id` запрещает вторую ревизию. Взаимные FK требуют полного комплекта к COMMIT и исключают ссылку существа на чужой снимок.
- Удаление связанных предков, ревизий, ссылок, профилей и каталога каскадом не допускается. FK используют NO ACTION; политика согласованного удаления пока не определена.

## 5. Инварианты и место проверки

| ID | Правило | Средство защиты |
|---|---|---|
| DB-I01 | Снимок — объект, base_id — строка, choices — массив из 0..15 объектов с целыми step и строковыми choice_id; посторонних ключей нет | CHECK с проверкой только текущего JSONB; предикат обязан вернуть TRUE, не NULL |
| DB-I02 | В choices ровно шаги 2..n, без дыр, дублей и перестановок | Проверка текущей строки функцией без чтения таблиц; совпадение номера в choice_id со step |
| DB-I03 | Допустимые база и варианты принадлежат неизменяемому каталогу этой ревизии | Межтабличная проверка при вставке ревизии; не CHECK с обращением к CatalogVersion |
| DB-I04 | Корень содержит только базу; версия равна активной версии кампании, проверенной под блокировкой | Транзакция создания и проверка ревизии |
| DB-I05 | Потомок сохраняет базу, каталог и весь префикс родителя, добавляя ровно один следующий вариант | Межстрочная проверка ревизии и построение снимка из серверных данных |
| DB-I06 | Кампания потомка совпадает с кампанией родителя; origin указывает на существующую ревизию | FK плюс межстрочная проверка; клиент не задаёт campaign/owner потомка |
| DB-I07 | Новый узел не продолжает вклад того же профиля напрямую | Сравнение owner родителя и нового узла; `SELF_CONTRIBUTION` |
| DB-I08 | Источник шага 16 не получает детей; максимум шагов — 16 | Проверка источника и снимка; `CHAIN_COMPLETE`; локальный предел массива |
| DB-I09 | Одна ссылка + один профиль дают одного потомка | Частичный UNIQUE `(origin_share_id,owner_profile_id) WHERE origin_share_id IS NOT NULL`; предложение P2 |
| DB-I10 | Одна ревизия имеет одну ссылку; точный ключ операции имеет один результат | UNIQUE ShareLink.source_revision_id и PK OperationReceipt |
| DB-I11 | Нет существа без единственной ревизии и нет committed pending receipt | Отложенные FK пары; deferred constraint trigger, читающий окончательное состояние receipt |
| DB-I12 | Общее число новых узлов кампании не превышает настроенную квоту | Блокировка строки Campaign для всех писателей, повторное чтение, проверка COUNT перед вставкой |

PostgreSQL CHECK не использовать как гарантию условий о других строках или таблицах; NOT NULL задавать явно. UNIQUE/FK и межстрочные проверки решают разные задачи. [Ограничения PostgreSQL](https://www.postgresql.org/docs/current/ddl-constraints.html).
Для JSON-предиката не помечать функцию IMMUTABLE, если она читает изменяемые таблицы. При изменении логики предиката проверять уже сохранённые строки.
Предлагается проверка наследования при INSERT ревизии и запрет UPDATE/DELETE зафиксированных Creature, CreatureRevision и ShareLink для прикладного пути записи.
Триггер наследования читает только существующий неизменяемый источник, вычисляет длины и сравнивает каждый элемент префикса по позиции; равенство «набора деталей» недостаточно.
Проверку новой записи нельзя заменять доверием к appearance из клиента: API принимает только base_id или один choice_id, а prefix собирает сервер.
Отложенный constraint trigger receipt должен быть AFTER ROW; к концу транзакции он повторно читает итоговую строку, а не проверяет старый образ pending. [CREATE TRIGGER](https://www.postgresql.org/docs/current/sql-createtrigger.html).
Ни индекс, ни триггер в этой версии не вводят политику D-01. Схема сохраняет необходимые owner/provenance для её последующей реализации.

## 6. Транзакция создания корня или потомка

Предлагаемый уровень — READ COMMITTED с явной общей блокировкой Campaign. Одна команда затрагивает одну кампанию; сетевых вызовов, ожидания человека и отправки сообщений внутри нет.

1. Backend подтверждает профиль, Origin/CSRF, форму запроса; определяет каноническую цель и нормализованное тело без доверия к owner из запроса.
2. Если существует completed receipt, сравнить цель и тело: совпадение возвращает сохранённый ответ; отличие даёт 409 `IDEMPOTENCY_KEY_REUSED` без изменений.
3. Начать транзакцию; захватить Campaign FOR UPDATE. После получения блокировки отдельным запросом заново прочитать receipt и сравнить цель/тело, если он уже завершён.
4. Зарезервировать receipt через INSERT ON CONFLICT DO NOTHING; при конфликте дождаться исхода конкурента, выполнить отдельный SELECT и сравнить цель/тело. Не использовать один CTE insert-or-select с прежним снимком.
5. После разрешения ключа backend проверяет source/expected_source_revision_id и choice_id по следующему шагу закреплённого каталога. SOURCE_MISMATCH, CHAIN_COMPLETE или INVALID_CHOICE откатывают pending receipt; ошибочный ввод не маскируется найденным ребёнком. Только после этих проверок искать потомка по `(origin_share_id,owner_profile_id)`. Существующий ребёнок при новом ключе завершает зарезервированный receipt ответом 200 existing=true с первым вкладом; выполнить COMMIT и вернуть результат без проверки/расхода квоты.
6. Совпадение ключа с иной целью/телом имеет приоритет над P2, в том числе при конкуренции разных кампаний. Pending другого запроса не является успешным ответом; быстрый путь до Campaign-lock допускает только completed receipt.
7. Для действительно нового узла проверить доступность кампании и запрет self; D-01 до решения остаётся блокером полной проверки eligibility.
8. У корня сверить переданный catalog_version с активным под той же блокировкой. У потомка брать каталог из источника, даже если активная версия кампании уже другая.
9. После возврата всех существующих результатов подсчитать Creature данной кампании под Campaign-lock; если COUNT достиг max_creatures — 429 `CAMPAIGN_LIMIT`, полный rollback.
10. Вставить Creature, затем единственную CreatureRevision. Снимок корня: выбранная база и []; снимок потомка: точная копия базы/choices родителя + один новый элемент.
11. Завершить receipt исходными 201 и `ContributionResult {creature,existing:false}`. Проверки пары, наследования и completed receipt должны пройти до успешного COMMIT.
12. Только после подтверждённого COMMIT отдавать успех. Обрыв ответа после COMMIT оставляет результат неизвестным клиенту; повтор сохраняет профиль, ключ, цель и тело.

Все пути вставки новых узлов и изменения квоты/активного каталога соблюдают блокировку Campaign. Второй скрытый писатель без этого протокола запрещён.
Вместо отдельного изменяемого счётчика квоты используется COUNT по индексу campaign_id; стоимость проверяется на согласованном объёме. Оптимизация счётчиком требует отдельного доказательства синхронизации.
Конфликт уникальности дочернего узла не перезаписывает первый выбор: после ожидания читается существующий результат. Сам UPDATE существующего узла не является способом дедупликации.
Ошибка любой стадии откатывает новый узел, ревизию и pending receipt целиком; ошибочный запрос не резервирует квоту навсегда.
При deadlock/serialization failure или неизвестном результате коммита повторяется вся команда по правилам backend; бесконечный автоматический retry не допускается. Пределы времени/повторов задаются до запуска.
Ожидание конфликтующего INSERT и свежесть следующего SELECT проверяются на выбранной версии PostgreSQL. [Изоляция транзакций](https://www.postgresql.org/docs/current/transaction-iso.html).

## 7. Выпуск ссылки и события

Выпуск ссылки — отдельная короткая транзакция: проверить владельца неизменяемого узла, receipt, получить или вставить ShareLink, завершить receipt, COMMIT.
Токен генерируется CSPRNG и не выводится из последовательного ID; случайный конфликт public_token вызывает генерацию другого токена, а не замену чужой ссылки.
UNIQUE(source_revision_id) разрешает гонку двух новых ключей: одна новая ссылка получает 201, конкурирующая команда — существующую с 200; точный replay сохраняет исходный статус.
Корень или потомок не создаются при выпуске/открытии ссылки. Для шага 16 ссылка разрешает просмотр, дерево и CTA, но не новый вклад.
ClientEvent вставляется отдельно от перехода CTA; пара `(profile_id,event_id)` исключает технический дубль в пределах профиля. Другой профиль с таким же event_id не конфликтует с этой строкой.
Повтор той же пары с тем же kind/контекстом даёт 200 duplicate; иной kind или контекст — 409 `IDEMPOTENCY_KEY_REUSED`. Первая строка не меняется; канонический контекст сравнивается после проверки доступа, без сохранения сырого share_token.
Для контекста share_token backend разрешает исходный creature; для creature_id проверяет владение. Требуется ровно один контекст. Событие не подтверждает заявку, оплату или пересылку.

## 8. Чтение, API и индексы

| Запрос API | Источник / ограничения | Индекс или ключ |
|---|---|---|
| POST/GET session | AnonymousProfile; GET возвращает только собственные profile_id и csrf_token; секрет не возвращается телом | UNIQUE session_secret_hash; PK id |
| GET campaigns/catalogs | Campaign и CatalogVersion; manifest старой версии остаётся доступен | UNIQUE Campaign.slug; PK CatalogVersion.version |
| GET creatures/{id}, me/creatures | Creature + единственная Revision; фильтр owner обязателен; публичный CreatureView не включает профиль | PK id; `(owner_profile_id,created_at,id)` |
| GET shares/{token} | ShareLink → Revision → Creature → Campaign; next_step/options вычисляются из длины и каталога | UNIQUE public_token; PK ревизии и существа |
| GET family | Только непосредственные дети разрешённого parent; каждый элемент содержит CreatureView и has_children | UNIQUE source_revision_id; `(origin_share_id,created_at,id)` |
| Новый вклад / квота | Campaign-lock, P2 и COUNT Creature по campaign_id | Частичный UNIQUE P2; `(campaign_id)` |
| Повтор команды | Receipt по точной тройке, сравнение нормализованных цели и тела | Составной PK receipt |
| Учёт CTA | ClientEvent, профиль из сессии, принадлежность кампании через Creature | PK `(profile_id,event_id)`; `(creature_id,received_at)` при запросах по контексту |

Family принимает `parent_id?`, `limit?`, `cursor?`; parent по умолчанию равен разрешённому корню запроса. Результат: `{root_id,parent_id,items:[{creature,has_children}],next_cursor}`.
Перед чтением детей backend проверяет, что parent находится в разрешённом поддереве: подъём по единственному пути происхождения не более чем на 15 рёбер.
Для прямых детей получить ShareLink родительской ревизии; если ссылки нет — детей нет. Выборка по origin_share_id не требует обхода всех ветвей.
Порядок — `(created_at,id)`; next_cursor связан с root, parent и последней парой. Подмена области курсора не должна открыть другое поддерево.
has_children проверяется EXISTS по ссылке ревизии текущего узла и индексу origin_share_id; не считать всё поддерево ради булевого признака.
Между страницами API не обещает единый snapshot: новые committed дети могут появляться. Предел limit задаётся до запуска; OFFSET и полный обход широкого дерева не обязательны.
GET не записывает Creature, Revision, ShareLink или receipt. Публичные ответы не содержат owner_profile_id, session_secret_hash и токены соседних узлов.
JSONB GIN, секционирование, кэш полных деревьев и дополнительные агрегаты без измеренного запроса не требуются. Плановые индексы проверить EXPLAIN на репрезентативной нагрузке.

## 9. Доступ, ошибки и эксплуатационная защита

Браузер не подключается к БД; сетевой доступ разрешён backend и закрытой эксплуатации. Прикладная роль не является superuser и не владеет схемой.
Предлагается отделить runtime, миграции/владельца схемы, резервирование и восстановление. Runtime не отключает триггеры, не меняет каталог/квоту и не выполняет произвольный DELETE/DDL.
Прикладная запись проходит через ограниченные команды с общими проверками; конкретные GRANT и способ защищённого захвата Campaign согласовать с реализацией, не выдавая runtime произвольный UPDATE конфигурации ради row lock.
Доступ к таблицам не заменяет проверки owner/campaign/subtree в backend. Если выбран механизм RLS, его политика и пул соединений требуют отдельной приёмки; наличие RLS здесь не заявляется.
Секреты подключения находятся вне репозитория и клиентского кода; параметры SQL передаются отдельно. В логах нет cookie, полных public_token и response_body receipt.
Backend сохраняет общий Error DTO и переводит известные нарушения в согласованные коды; необработанный текст SQL, имя сервера и стек клиенту не передаются.
Семантические ошибки: 409 `SOURCE_MISMATCH`, `SELF_CONTRIBUTION`, `CHAIN_COMPLETE`, `CATALOG_CHANGED`, `CAMPAIGN_CLOSED`, `IDEMPOTENCY_KEY_REUSED`; неправильный выбор — 422 `INVALID_CHOICE`.
Отсутствующий/чужой объект — 404 `NOT_FOUND`; недоступное хранение — 503 `TEMPORARILY_UNAVAILABLE`; лимит кампании — 429 `CAMPAIGN_LIMIT`. Остальные коды и приоритеты — по ТЗ backend.
Распределение прав — проверяемая часть будущей миграции, а не выполненная настройка. [Права PostgreSQL](https://www.postgresql.org/docs/current/ddl-priv.html).

## 10. Миграции и откат

Перед реализацией выбрать поддерживаемую версию PostgreSQL и сверить необходимые ограничения, JSONB-функции, deferrable-проверки и драйвер с её документацией.
Первичная миграция создаёт таблицы, ограничения, индексы, проверки и права; данные кампании/каталога загружаются отдельно с согласованными значениями. В этом задании SQL не создаётся.
Проверить миграцию на чистой БД и на копии предыдущей схемы, если такая появится; зафиксировать версию и контрольную сумму миграции.
Изменение JSON-формата, ключей receipt или правил источника считается изменением контракта; простого успешного запуска ALTER недостаточно.
Совместимый выпуск сначала расширяет схему, затем обновляет backend; удаление старых полей/ограничений — после прекращения их использования и проверки данных.
Откат приложения не означает безопасный откат БД. После новых записей предпочтительна исправляющая миграция; разрушительное восстановление требует плана согласования потерянных/новых вкладов и отдельного разрешения.
До изменения статуса старых данных проверить непрерывность префиксов, единственность пары, P2, ссылки, завершённость receipt и принадлежность кампаний. Не «исправлять» нарушения молчаливой обрезкой истории.

## 11. Резервирование и восстановление

В резерв входят согласованная копия всех таблиц, схема/миграции, роли и права, конфигурация кампании и все версии файлов каталога, на которые существуют ссылки.
Копия хранится отдельно от рабочего диска; доступ закрыт. Она содержит приватные профили и receipt, поэтому не является публичным артефактом.
Предлагаемый начальный механизм — согласованный логический backup; окончательный выбор определяется объёмом, RPO/RTO и требованием восстановления на момент времени, которых пока нет.
pg_dump даёт согласованный снимок одной БД; роли не входят в обычный dump одной базы и требуют отдельного учёта. Версии внешних ассетов фиксируются в манифесте комплекта. [SQL Dump](https://www.postgresql.org/docs/current/backup-dump.html).
Частота, retention, шифрование/ключи, допустимая потеря данных и ответственный задаются до внешнего теста. Не обещать нулевую потерю при наличии только файла копии.
Восстановление проверить в отдельной среде: ограничения и права, ссылки, старые каталоги, пары узел/ревизия, дерево, receipt и повтор уже выполненной команды.
Возврат более старой копии может убрать ранее подтверждённые узлы/receipt и изменить гарантии повтора. Такой исход должен быть явно обработан планом восстановления; целевые сроки пока не заявляются.

## 12. Подготовленная приёмка

Ни один сценарий ниже не исполнен. Результат PASS появится только после миграции/реализации на выбранной версии PostgreSQL и фиксации наблюдаемых строк/ответов.

| Проверка | Наблюдаемый результат |
|---|---|
| T01 Корень B01/B02/B03 | Один Creature, одна Revision, step=1, choices=[], completed receipt; иной base отклонён |
| T02 Наследование n→n+1 | Сохранён весь упорядоченный префикс, добавлен один допустимый вариант следующего шага |
| T03 Подмена/дырка/перестановка | Нельзя commit snapshot с изменённым предком, пропущенным шагом, чужой базой или каталогом |
| T04 Два профиля, одна ссылка | Два независимых ребёнка; источник не изменён; изменение локального preview не меняет БД |
| T05 Один профиль, два ключа и разных выбора | Одна дочерняя строка; второй результат 200 existing=true с первым выбором; у каждого ключа свой completed receipt |
| T06 Тот же ключ, иное тело/цель | 409 IDEMPOTENCY_KEY_REUSED; нет второго узла, подмены receipt и расхода квоты |
| T07 Потеря ответа после COMMIT | Повтор возвращает исходные статус/тело/ID; количество узлов и ревизий неизменно |
| T08 Сбой до COMMIT / pending | Нет опубликованной половины пары, потраченной квоты или committed pending receipt |
| T09 Self и финал | Собственная ссылка → SELF_CONTRIBUTION; step16 → CHAIN_COMPLETE; просмотр финала и выпуск ссылки работают |
| T10 Изменение активного каталога | Старый потомок наследует старую версию; новый корень со старой указанной версией → CATALOG_CHANGED |
| T11 Последнее место, два конкурентных запроса | После первого COMMIT второй видит свежий COUNT и CAMPAIGN_LIMIT; при rollback первого место доступно второму |
| T12 Повтор при исчерпанной квоте | Receipt и существующий ребёнок возвращаются; нет новой строки и повторного учёта квоты |
| T13 Два выпуска ссылки | Одна ShareLink на ревизию; корректные 201/200 и точный replay; токен не выдаётся постороннему владельцу |
| T14 Family / широкое дерево | Только дети выбранного parent; подъём ancestry ограничен 15 рёбрами; курсор другого root/parent отклонён |
| T15 GET / события | GET не создаёт бизнес-строк; та же пара profile/event и контекст → 200 без дубля, иной контекст/kind → 409; другой профиль с тем же event_id создаёт собственное событие; отказ аналитики не блокирует CTA |
| T16 Права runtime | Нельзя изменить предка, профиль владельца, каталог, квоту, завершённый receipt, удалить историю или отключить проверки |
| T17 Пара / каталог | Коммит существа без ревизии и второй ревизии запрещён; старые версии каталога не заменяются на месте |
| T19 Неверный ввод при existing | После receipt, но до P2 неверные expected source/choice дают SOURCE_MISMATCH/INVALID_CHOICE и rollback; верная другая опция возвращает первый вклад |
| T18 Restore | В отдельной среде восстановлены данные, ограничения, права и ресурсы; проверены исходные ссылки/дерево/повтор команды |

Для гонок сохранять порядок BEGIN/lock/INSERT/COMMIT, профили, ключи и окончательные строки; два последовательных запроса не заменяют конкурентную проверку.

## 13. Открытые решения и условия выпуска

- D-01: возвращение более раннего участника в ту же ветвь; до решения не добавлять UNIQUE по profile/root/campaign и не заявлять полную готовность eligibility.

- Версия PostgreSQL, размещение/регион, транспорт, роли и обработка данных: нужны до развёртывания.
- Полный совместимый каталог 16×3: сейчас созданы 12 PNG, ещё 36 вариантов не подготовлены; пригодность размещения на трёх базах не подтверждена. БД не делает этот каталог готовым.
- Нагрузка, размер дерева, limit страницы, max_creatures, размер/время транзакции и лимиты retry: нужны до оценки ресурсов и внешнего теста; числовые значения не выдуманы.
- RPO/RTO, расписание копий, срок хранения, ответственный и практический restore: нужны до внешнего теста.
- Бренд, оффер, CTA и смета в пределах 10 000 ₽: пока не заданы/не подтверждены; это ТЗ не разрешает расходы или публикацию.
