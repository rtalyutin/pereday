# Передай — ТЗ на бэкенд v0.1

Дата: 22 сентября 2026. Результат: проект спецификации, не реализованный сервис. Механика «каждый участник делает один шаг и передаёт дальше» подтверждена пользователем. Описанные HTTP-контракты, сессии и ограничения повторов — предлагаемый способ её реализации. Предложение P3 об анонимном профиле браузера не является подтверждением личности человека.

Связанные документы: [ТЗ фронтенда](Frontend-TZ.md), [ТЗ БД](Database-TZ.md), [каталог 16 шагов](Catalog-TZ.md). При конфликте со старой архитектурой приоритет имеет подтверждённая механика и единый проект API этих трёх ТЗ. D-01 в §11 остаётся открытым и блокирует только зависимое правило повторного участия, а не подготовку остальных разделов.

## 1. Назначение и границы

Бэкенд сохраняет вклад участника, выдаёт ссылку на его неизменяемый результат, создаёт независимых потомков с одним следующим выбором и показывает происхождение. Отдельно предоставляет бренд/оффер/CTA студии и принимает сообщения о кликах. Демо продаёт разработку подобных маркетинговых инструментов; создание существа и переход по CTA не являются оплатой или подтверждённой заявкой.

Предлагаемая структура: один backend с модулями сессий, вкладов, передачи/идемпотентности, дерева/кампании/событий. Единственное транзакционное хранилище — PostgreSQL. Frontend и API доступны через один HTTPS-origin. Язык, фреймворк, хостинг, точная версия PostgreSQL и числовые эксплуатационные лимиты не выбраны. Микросервисы, очередь, WebSocket, платёж, CRM, публичная админка и вызов ImageGen на пользовательском ходе не требуются этим ТЗ.

## 2. Правила и переходы

| ID | Правило | Наблюдаемый результат |
|---|---|---|
| BE-R01 | Корень создаётся с одной базой B01/B02/B03 | Узел шага 1, дополнений нет |
| BE-R02 | Потомок добавляет ровно следующий шаг | У родителя n, у ребёнка n+1; прежние выборы идентичны |
| BE-R03 | На каждом следующем шаге три варианта | Ранее выбранные элементы не исключают ни один вариант |
| BE-R04 | Каждый запрос вклада фиксирует один выбор | Клиент не передаёт полный изменённый облик, номер шага или владельца |
| BE-R05 | Вклад неизменяем после успешной фиксации | Произвольного POST/PATCH редактирования, замены базы/выборов предков нет |
| BE-R06 | Несколько получателей создают разные ветви | Исходный узел и соседи не меняются |
| BE-R07 | 16 — завершённый шаг | Ни потомка шага 17, ни добавления к завершённому узлу |
| BE-R08 | Один профиль по одной ссылке получает один результат — проект P2 | Повтор не увеличивает число узлов; сохранён первый выбор |
| BE-R09 | Профиль не продолжает собственный узел | SELF_CONTRIBUTION; нет обхода через прямой запрос API |
| BE-R10 | Просмотр не является вкладом | GET и превью мессенджеров не создают существа или ссылки |
| BE-R11 | Версия каталога наследуется | Новая активная версия кампании не меняет существующую ветвь |
| BE-R12 | Ссылка показывает сохранённый снимок | Публичный токен не даёт права владения; ссылка может быть передана нескольким людям |

Состояния узла вычисляются: `step < 16` — можно продолжить другим участником; `step = 16` — завершён. Записанного «пустого потомка», состояния «выбирает» и изменяемого серверного черновика нет. Предпросмотр до подтверждения существует на frontend. Возможность отменить или исправить уже зафиксированный вклад не задана и не входит в API этой версии.

Путь: автор выбирает базу → подтверждает корень → получает ссылку → получатель открывает → выбирает один следующий элемент → подтверждает → получает собственного потомка → выпускает свою ссылку. Последний участник выбирает дополнение шага 16; результат доступен для просмотра, дерева и CTA. Выдача ссылки на финал использует тот же проектный механизм, но не разрешает продолжение.

## 3. Сессия и права

1. `POST /session` выполняет только bootstrap. Валидная существующая сессия переиспользуется. Запрос проверяется на same-origin; бизнес-сущности не создаются.
2. `GET /session` с cookie подтверждает профиль и возвращает `{csrf_token, profile_id}`. `profile_id` — собственный несекретный идентификатор для привязки pending-команд, не средство авторизации. При отсутствии/невалидности cookie — 401.
3. Создающие бизнес-команды допускаются только после подтверждения профиля. Потерянный ответ bootstrap не должен совмещаться с созданием необнаружимого потомка.
4. Cookie предлагается `__Host-peredai_sid; Secure; HttpOnly; Path=/; SameSite=Lax`, без Domain. В хранилище — проверяемое представление случайного секрета; сам секрет не возвращать в JSON, URL и localStorage. Срок жизни — D-04. [Семантика cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie).
5. У бизнес-POST и `/events` проверять Origin и CSRF-токен, связанный с сессией. SameSite не заменяет эту проверку; произвольный credentialed CORS не разрешать. [OWASP CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).
6. Cookie — единственный источник полномочий. Параметры `owner_profile_id`, чужой профиль, подмена campaign или полного облика во входе отклоняются. Своё чтение по ID требует владельца; чужой ID возвращает 404.
7. Публичные ссылки дают чтение конкретного снимка/его поддерева и возможность предложенного следующего вклада. Идентификаторы профилей, секреты, чужие share-токены и внутренние журналы не выдаются.

Профиль браузера не равен уникальному человеку: другой браузер, очищенная cookie или устройство могут создать другой профиль. Требование «один шаг» нельзя рекламировать как защиту от повторного участия физического человека без отдельной модели идентификации. Согласовать эту границу до внешнего запуска.

## 4. HTTP-контракт

Префикс всех путей — `/api/v1`. Запросы/ответы — JSON. Динамические ответы, ошибки и ответы с зависимостью от сессии — `Cache-Control: no-store`. Неизменяемые публичные манифесты/ассеты допускают версионное кэширование. Публичная страница — `/s/{token}`. Неизвестные поля команд отклоняются, значения проверяются по опубликованной версии каталога.

| Метод и путь | Доступ и вход | Успех |
|---|---|---|
| POST `/session` | Same-origin bootstrap, `{}` | 200, cookie установлена/переиспользована; затем GET подтверждения |
| GET `/session` | Cookie | 200, `{csrf_token,profile_id}` |
| GET `/campaigns/{slug}` | Публичный | 200, `{slug,brand,offer,cta_target,active_catalog_version,accepts_contributions}` |
| GET `/catalogs/{version}` | Публичная опубликованная версия | 200, immutable manifest; неизвестная/неопубликованная — 404 |
| POST `/creatures` | Сессия, CSRF, Idempotency-Key; `{campaign_slug,catalog_version,base_id}` | 201 `ContributionResult`, step=1 |
| GET `/me/creatures` | Сессия; `limit?`, `cursor?` | 200, `{items:[CreatureView],next_cursor}` |
| GET `/creatures/{id}` | Владелец | 200 `CreatureView` |
| POST `/creatures/{id}/shares` | Владелец, CSRF, Idempotency-Key; `{}` | 201 новая или 200 существующая `ShareView` |
| GET `/shares/{token}` | Публичный, cookie необязательна | 200 `SharePreview`; никаких записей |
| POST `/shares/{token}/offspring` | Сессия, CSRF, Idempotency-Key; `{expected_source_revision_id,choice_id}` | 201 новый или 200 существующий `ContributionResult` |
| GET `/shares/{token}/family` | Публичный токен; `parent_id?`, `limit?`, `cursor?` | 200 `FamilyPage` в границах поддерева |
| GET `/creatures/{id}/family` | Владелец; те же query | 200 `FamilyPage` в границах своего поддерева |
| POST `/events` | Сессия, CSRF; `{event_id,kind,share_token? либо creature_id?}` | 202 принято или 200 duplicate |

`kind` этой версии — только `cta_click_reported`. В событии требуется ровно один контекст: валидный public share_token или свой creature_id; кампанию сервер выводит из контекста. Событие получает серверное время. Повтор `(profile_id,event_id)` с другим нормализованным содержимым — 409 IDEMPOTENCY_KEY_REUSED; чужой контекст не принимается.

GET-запросы никогда не создают профиль, узел, ссылку или событие. Установить лимиты размера JSON, длины строк/ключей, количества выдаваемых строк и частоты запросов конфигурацией; их численные значения должны быть выбраны до внешнего теста. UUID в примерах — условные идентификаторы, не существующие объекты.

### 4.1. Типы данных

| Тип/поле | Смысл и ограничения |
|---|---|
| `Appearance.base_id` | Одна база B01/B02/B03 из закреплённой версии каталога |
| `Appearance.choices` | Упорядоченный массив `{step,choice_id}`; ровно шаги 2..step без пропусков/дубликатов |
| `CreatureView` | `{id,campaign_slug,revision_id,step,total_steps:16,catalog_version,appearance,is_complete}` |
| `step` / `is_complete` | Целое 1..16; is_complete выводится как step==16, не принимается от клиента |
| `ContributionResult` | `{creature:CreatureView,existing:boolean}` |
| `ShareView` | `{url,token,source_revision_id}`; URL на согласованном origin, токен непредсказуемый CSPRNG |
| `SharePreview` | `{creature,brand,offer,cta_target,next_step,options,viewer}` |
| `options` | Для узлов 1..15 ровно три `{choice_id,label,preview_asset}` следующего шага; для 16 — пустой массив |
| `next_step` | step+1 для 1..15; `null` для 16 |
| `viewer` | `{state,existing_creature_id:null\|id}`; идентификатор результата только этого профиля |
| `FamilyPage` | `{root_id,parent_id,items:[{creature:CreatureView,has_children:boolean}],next_cursor:null\|string}` |
| `Error` | `{error:{code,message,request_id,details?}}`; без SQL, stack trace и секретов |

`viewer.state` для шага 16 всегда `complete`, в том числе без cookie. Для 1..15: без cookie — `needs_session`; собственный исходный узел — `self`; существующий вклад профиля по ссылке — `already_contributed`; закрытая кампания — `unavailable`; допустимый новый участник — `choose`. Сначала проверять существующий результат, затем доступность новых вкладов. Сценарий возврата предка D-01 ещё не имеет утверждённого решения и не должен молча попадать в `choose` или `self`.

### 4.2. Пример одного перехода

Публичная ссылка указывает на шаг 1 с B01, catalog_version=`demo-1`, revision_id=`11111111-1111-4111-8111-111111111111`. Новый получатель выбрал глаз-яичницу:

```http
POST /api/v1/shares/{token}/offspring
Content-Type: application/json
Idempotency-Key: 22222222-2222-4222-8222-222222222222
X-CSRF-Token: {csrf_token}

{"expected_source_revision_id":"11111111-1111-4111-8111-111111111111","choice_id":"02A"}
```

```json
{
  "creature": {
    "id": "33333333-3333-4333-8333-333333333333",
    "campaign_slug": "demo",
    "revision_id": "44444444-4444-4444-8444-444444444444",
    "step": 2,
    "total_steps": 16,
    "catalog_version": "demo-1",
    "appearance": {"base_id":"B01","choices":[{"step":2,"choice_id":"02A"}]},
    "is_complete": false
  },
  "existing": false
}
```

HTTP 201 выдаётся только после COMMIT. Из этого результата пользователь создаёт отдельной командой свою ссылку. Ссылка родителя остаётся ссылкой на шаг 1.

### 4.3. Ошибки

| HTTP / code | Причина | Ожидаемая реакция frontend |
|---|---|---|
| 401 SESSION_REQUIRED | Нет действующего профиля | Проверить сессию; pending не повторять автоматически как нового участника |
| 403 CSRF_REJECTED | Нарушена проверка запроса | Обновить подтверждение той же сессии; не обходить защиту |
| 404 NOT_FOUND | Неизвестная ссылка, каталог или недоступный ID | Понятное состояние недоступности, без раскрытия владельца |
| 409 IDEMPOTENCY_KEY_REUSED | Тот же ключ, другая цель/содержимое | Не создавать новый ключ автоматически, показать конфликт |
| 409 SOURCE_MISMATCH | expected_source_revision_id не совпал со ссылкой | Перечитать исходный снимок и сбросить неподтверждённый предпросмотр |
| 409 SELF_CONTRIBUTION | Попытка продолжить свой узел | Показать свой результат и передачу другим |
| 409 CHAIN_COMPLETE | Попытка нового шага после 16 | Показать финальный результат, дерево, CTA |
| 409 CATALOG_CHANGED | Новый корень с уже неактивной версией | Загрузить текущий каталог и запросить новый осознанный выбор |
| 409 CAMPAIGN_CLOSED | Кампания не принимает новые узлы | Чтение/возврат существующего результата сохраняются |
| 422 INVALID_CHOICE / INVALID_REQUEST | Опция не из следующего шага, неизвестное поле, неверная форма | Исправить неподтверждённый ввод; записей нет |
| 429 RATE_LIMITED / CAMPAIGN_LIMIT | Частотный лимит / квота новых узлов | Различать причины; Retry-After только для временного ограничения |
| 503 TEMPORARILY_UNAVAILABLE | Хранилище/зависимость недоступна | При неизвестном исходе повторить исходную команду, не создавать новый вклад |

`next_cursor` непрозрачен клиенту. Неверный курсор/неположительный или превышающий настроенный максимум limit — 422 INVALID_REQUEST. Сервер не интерпретирует непроверенные части курсора как SQL.

## 5. Идемпотентность и атомарность

Для `create_root`, `create_offspring`, `create_share` ключ обязателен. Область receipt — `(profile_id,operation_type,idempotency_key)`. Нормализованные цель и тело сохраняются/хешируются; одинаковый JSON с другим порядком полей не должен становиться другой командой. Цель включает конкретную ссылку или creature_id. Не использовать сырой секрет cookie в receipt.

| Случай | Результат |
|---|---|
| Тот же профиль, операция, ключ, цель и тело | Исходные HTTP-статус и тело успешного receipt; новый эффект отсутствует |
| Тот же ключ, другая цель/тело | 409 IDEMPOTENCY_KEY_REUSED |
| Другой ключ, тот же профиль и исходная ссылка | 200 existing=true, первый сохранённый потомок, даже если вновь выбрана другая допустимая опция |
| Два разных профиля по одной ссылке | Два независимых потомка, при наличии квоты |
| Таймаут после COMMIT | Исход неизвестен для клиента; повтор получает зафиксированный результат |
| Ошибка до COMMIT | Узел, revision и receipt не остаются частично сохранёнными |

Ошибки валидации и откатившиеся транзакции не сохраняются как успешный receipt. При повторе после сетевой неопределённости сначала разрешить receipt, затем принимать решение о доступности новых записей. Наличие лимита или закрытие кампании не должно превращать уже совершённый вклад в отказ бизнес-квоты; частотная защита может временно отложить сам запрос.

### 5.1. Транзакция потомка

1. Проверить сессию, Origin/CSRF, форму запроса и частотные ограничения; найти source link и каноническую цель. Быстрый путь разрешён только для completed receipt: сравнить цель/тело и вернуть replay либо 409.
2. Начать короткую транзакцию, заблокировать Campaign. После ожидания отдельным запросом повторно прочитать receipt. Совпадение — replay, несовпадение — 409.
3. Зарезервировать receipt через INSERT ON CONFLICT DO NOTHING. При конфликте дождаться исхода конкурента и отдельным SELECT сравнить цель/тело: ключ мог одновременно использоваться в другой кампании. Не возвращать бизнес-дубликат до разрешения конфликта ключа.
4. До P2 проверить expected_source_revision_id против неизменяемого источника и принадлежность choice_id ровно следующему шагу его каталога. Несовпадение — SOURCE_MISMATCH, отсутствие следующего шага — CHAIN_COMPLETE, неверная опция — INVALID_CHOICE; откатить незавершённый receipt. Затем найти `(origin_share_id,owner_profile_id)`. Если потомок существует, завершить receipt текущего нового ключа с 200 existing=true и вернуть первый результат после COMMIT. Другая вновь присланная опция не меняет первый выбор; доступность кампании и квоту для возврата не проверять.
5. Для действительно нового вклада проверить отсутствие прямого самопродолжения и остальные правила eligibility. D-01 требует отдельного решения до выпуска полной проверки eligibility. Под удерживаемой блокировкой проверить accepts_contributions и оставшуюся квоту.
6. Скопировать неизменяемый префикс родителя и добавить один выбор; campaign/catalog/base/step вывести сервером. Создать Creature, единственную CreatureRevision и completed receipt в той же транзакции. Модель хранения — из ТЗ БД.
7. COMMIT; только затем отправить ответ. Ошибка связи на границе COMMIT не доказывает отсутствие создания.

Для конфликтующего `INSERT ... ON CONFLICT DO NOTHING` предусмотреть последующий отдельный `SELECT` в Read Committed: результат конкурента может не входить в снимок самого INSERT. Один CTE insert-or-select не заменяет этот порядок. [PostgreSQL: изоляция](https://www.postgresql.org/docs/current/transaction-iso.html).

Все команды создания корней и потомков соблюдают единый порядок: быстрый completed receipt → Campaign lock → повтор/резервирование receipt → валидация источника/опции → существующий результат → eligibility и квота → создание. Это простое проектное решение последовательно расходует квоту внутри кампании; пропуск блокировки одной командой разрушает гарантию последнего места. Время блокировки не включает ожидание пользователя, внешнюю сеть или отправку ссылки. [PostgreSQL: блокировки](https://www.postgresql.org/docs/current/explicit-locking.html).

### 5.2. Корень и ссылка

- **Корень:** сначала replay receipt; под Campaign lock проверить доступность, requested catalog_version против active_catalog_version и базу, затем квоту. Создать step=1 с пустым choices и единственной revision. Повтор старого успешного корня не отвергать из-за последующего переключения каталога.
- **Ссылка:** проверка владельца, receipt, поиск по source_revision_id. Существует — 200 с той же ссылкой; нет — сгенерировать непредсказуемый токен CSPRNG, создать ShareLink с UNIQUE(source_revision_id) и UNIQUE(token), сохранить receipt, COMMIT. Внешнего вызова мессенджера нет. Шаг 16 не запрещает выдачу ссылки для просмотра.
- Конкурирующие выпуски ссылки с разными ключами должны получить одну каноническую ссылку. Коллизия случайного токена обрабатывается повторной генерацией; последовательный ID не заменяет непредсказуемость.

## 6. Каталог, снимки и ассеты

Опубликованный каталог включает ровно 16 шагов по 3 опции: 3 базы + 45 дополнений. Manifest определяет ID, подписи, версии ресурсов, размеры/границы изображения, точки крепления, масштаб и порядок слоёв для каждой базы. Точная JSON-структура manifest, единицы и формула размещения — в §8.1 ТЗ frontend. `options[].preview_asset` — строка URL из `manifest.assets[option.asset_id].src`, а не произвольный объект координат; полная композиция строится через закреплённый manifest. Сервер принимает только ID опции своего следующего шага и своей закреплённой версии; произвольные URL, HTML, графические файлы и координаты не принимаются.

Сейчас созданы 12 PNG RGBA 1254×1254: три базы и девять дополнений шагов 2–4. Остальные 36 ассетов шагов 5–16 не созданы; координаты совмещения не проверены. Публикация полного каталога требует готовности всех вариантов и проверки совместимости. Нельзя скрыть отсутствующий третий выбор, молча заменить рисунок или выдать неполный каталог за полный 16-шаговый режим.

Каталог родителя закреплён в revision; child наследует ту же версию. Переключение Campaign.active_catalog_version влияет на новые корни. Используемые старые файлы не удалять при релизе. Публикация каталога и изменение его содержимого — закрытая операция поставки, не пользовательский API.

## 7. Дерево, выдача и CTA

`family` возвращает порцию **непосредственных детей** выбранного `parent_id`; без parent_id используется корень разрешённого поддерева. Разрешённый root — узел публичной ссылки или свой узел private endpoint. Проверять parent_id подъёмом по происхождению до root, не более 15 рёбер; выход за поддерево — 404. Само значение UUID не даёт доступа к соседней ветви.

Порядок детей — стабильный `(created_at,id)`. Курсор привязан к root_id, parent_id и последней позиции; его целостность проверяется сервером. Лимит/таймаут чтения настраиваются. Нет обещания единого снимка дерева между несколькими запросами; frontend раскрывает узлы порциями и дедуплицирует ID. `has_children` вычисляется существованием реального потомка, не событиями просмотра/передачи.

В FamilyPage нет профилей, токенов других узлов или секретов. Корневой снимок frontend получает из своего CreatureView/SharePreview; сервер не добавляет невидимых предков из-за курсора. Счётчики вкладов, если выводятся, должны опираться на зафиксированные сущности, а не количество запросов или receipt.

CTA берётся из согласованной конфигурации Campaign и открывается браузером напрямую. POST /events выполняется отдельно, best effort. Отсутствие сессии или ошибка аналитики не препятствует переходу. Статистика кликов неполна и не доказывает обращения/выручку. Не делать серверный запрос по произвольной цели CTA и не принимать её из тела пользовательской команды.

## 8. Защита и эксплуатация

- Валидировать размер/форму входа до дорогих запросов; использовать параметризованный SQL. Враждебные строки не исполняются и не попадают в HTML без экранирования.
- Квота Campaign и rate limiting решают разные задачи. Не считать IP или cookie доказательством уникального человека. Не вводить неограниченные повторные попытки при сбоях.
- БД недоступна из браузера; отдельные права приложения, миграции и резервирования. Секреты вне frontend и публичного репозитория.
- Журналы: request_id, операция, код/длительность, replay/existing/new; без cookie, CSRF, полного токена URL. Referrer-Policy должен предотвращать передачу public token внешнему CTA.
- Метрики: ошибки/задержки, конфликты и повторы, заполнение квоты, соединения/диск БД, результат резервирования. SLA и численные пороги не заявлены без нагрузки и сметы.
- Согласованное восстановление БД и версий ресурсов обязательно; старый backup способен изменить наблюдаемую историю и доступность receipt. Retention/RPO/RTO остаются открытыми, автоматическая очистка не разрешена этим ТЗ.
